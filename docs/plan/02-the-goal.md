# The goal

There are nine claims. Each one has a number or a predicate, each one can turn out false, and each one is checked by a command in `rucc-plan9`, never by a person reading a console. They follow bsd 02, with the changes Plan 9 brings:
- the reference compiler is kencc, not GCC;
- the build runs in a guest;
- half of the goal is a hosted runtime, not a build.

Throughout this folder:
- **R** is the rucc build.
- **G** is the reference build: the same tree, built in the same way, by kencc from the same pin (04.2).
- **"G passes"** means a test passed in all three of G's baseline runs.
- **H** is `9h`, the hosted runtime of document 10. **Q** is a real 9front kernel under QEMU. A GUI result is written as binary-on-kernel, so **R/H** means R's binaries on `9h`, and **G/Q** means G's binaries on a G kernel in QEMU.

## 02.1 Unmodified

The source tree is one of two things, checked by hash before every build:
- **The pinned commit.** The `front` commit of 04.1, fetched from the 9front repository or its GitHub mirror. `r9 fetch` checks that the commit hash matches.
- **A release's own tree.** The `/sys/src` and `/sys/include` of a release image, which is checked by SHA-256 against 9front's published sums. `r9 sets` maps it to a commit (01.1).

Nothing in the tree is patched. No file is added to the tree, and nothing in it is regenerated by us. The build writes where 9front's build writes: object files beside their sources, and installs into the guest root. Both are inside the build image, which is thrown away after each run (05.2).

Configuration is allowed. It must be one of the following, and every item applies to G as well.

**1. The architecture.** The `objtype` environment variable: `amd64` or `arm64` (later `386` and `arm`).

**2. A kernel configuration the tree ships.**

| `objtype` | Configurations | Notes |
|---|---|---|
| `amd64` | `pc64` | 9front's standard amd64 kernel |
| `arm64` | `qemu` | the QEMU virt kernel. It is headless (01.5) |
| `386` | `pc` | |

No configuration is written by us for the Q kernels. `9h`'s configuration is part of `9h`, not part of the tree (10.2).

**3. The compiler slot.** In the build's namespace, `/$objtype/bin/6c` (or `7c`) is the `r9-cc` shim, put there by `bind`. Plan 9 makes this kind of configuration ordinary: it changes no file, only the build process's view of the file system. The G build runs with the same shim in recording mode, forwarding to the real `6c`, so the two builds take the same path (05.4).

**4. The build commands.** These are the ones `sys/src/mkfile` documents and nothing more:
- `mk install` (or `mk release`);
- `mk kernels`;
- `mk test`;
- `mk clean`.

There is no `CFLAGS` override. If `CFLAGS` has to change for R to build, that is a rucc bug.

**What does not count as configuration:**
- removing a directory from a `DIRS` list;
- putting a stub before a program in the path;
- `R9_BRINGUP` delegations (14.4);
- a hand-edited `mkfile`.

Each of these makes a run ungraded.

## 02.2 Built

A build is complete when all of the following hold for the row:
1. `mk install` in `/sys/src` exits 0 with rucc in the compiler slot.
2. `mk kernels` exits 0, and the configuration of 02.1 is linked.
3. The census (05.6) shows that every `.c` unit for an `objtype` in the claim (`amd64`, and `arm64` from P4) went through rucc. Its `ref-c` count is 0. Units for other `objtype`s, which `mk kernels` builds for the board kernels and boot loaders (09.1), go to G's `8c`, `5c` and `vc` and are counted as `other-arch`. The count is reported, and it shrinks as P10 and P11 add architectures.
4. Every `.s` file went through the tree's own assembler (`ref-as`) until P6, and through rucc from P6 on.
5. `r9 tree-diff` shows that the set of installed files is identical to G's: the same names, the same modes, and no file missing or extra.

## 02.3 Correct

The image R builds is correct when all of the following hold:
- **It boots.** The R kernel with the R userland boots under QEMU to a `rio` session on amd64 (screen read back over `/dev/screen`) and to a shell on arm64, within the timeout of 12.3, with no console line G's boot does not print.
- **The tests pass.** `mk test` in the 13 test directories passes every case G passes (12.2).
- **The compiler fixed point holds.** `6c`, `6l`, `6a`, `7c`, `7l` and `7a` built by R, used to build the tree, produce `.6` and `.7` files and binaries byte-identical to those G's tools produce (12.4). kencc is deterministic, so any difference is a miscompile in the tool R built.
- **Deterministic programs agree.** Every program in the `diffrun` set produces byte-identical output under R and G on the same inputs (12.5). There are 40 programs: `troff` and `pic`, `gs`, the compressors, `libsec`'s digests and ciphers, `git` object hashes, `awk`, `sed`, `mk -n`, `hoc`, `bc`, and the image converters among them.
- **Every failure is attributed** by the 2x2 of 12.7 before it is filed: R kernel with G user space, and G kernel with R user space.

## 02.4 Versions

| Set | Members | Cadence |
|---|---|---|
| `current` | `front` at the pin, advanced weekly to the newest commit G builds and passes | nightly |
| `releases` | the current release (11952) and the previous one (11554) | weekly |

When a release is tagged, it joins `releases` the same day and the oldest member leaves. 9front has no maintenance branches, so there is nothing like bsd 02.4's stable branches.

## 02.5 Performance

Performance is measured on amd64 only, on server3, under QEMU/KVM with the guest pinned (13.2). The runtime claim is for R against G:

| Measure | Gate |
|---|---|
| Geometric mean of R/G time over the 40 benchmarks of 13.1 | ≤ 1.00 |
| Any one benchmark | ≤ 1.05 |
| Kernel text size | ≤ 1.25 × G |
| `libc.a` text size | ≤ 1.25 × G |

The geometric-mean gate is "no worse", not "within 2%", because kencc does almost no optimization and rucc at `-O2` should win clearly. The size gate allows rucc's inlining and alignment, within bounds that keep the kernel image and the boot media inside their limits.

Compile time has two parts:
- **The parent gate.** On the units GCC 16 can compile with `-fplan9-extensions` (13.5), rucc's CPU time is at most half of GCC 16 `-O2`'s.
- **Against kencc.** It is reported, not gated, until P0 has measured it. Open question 1 decides whether "twice as fast as `6c`" is a goal.

No rucc process may use more than 1 GB.

## 02.6 Architectures

| Order | `objtype` | Q (boot and tests) | H (`9h`) |
|---|---|---|---|
| 1 | `amd64` | QEMU/KVM on gpc and server3 | Linux amd64 (KVM) |
| 2 | `arm64` | QEMU TCG on gpc; QEMU/HVF on the M4 | macOS arm64 (HVF), Linux arm64 (KVM) |
| 3 | `386` | QEMU/KVM | none |
| 4 | `arm` | QEMU TCG (`virt`, if 9front's arm kernels boot there; open question 9) | none |

Intel Macs (HVF on x86) can run H for amd64. They are supported if a builder exists, and are not in the claim (17).

The Pi, Reform, Honeycomb, MNT, `xen`, `mtx`, `ppc`, `sgi` and the other board kernels are built by R in `mk kernels` wherever the configuration builds by default. They are not booted (09.4).

## 02.7 The GUI on the host

This is the claim that makes this folder different. It has five parts.

**Which programs.** The census is every program in the tree whose source calls `initdraw` (directly or through `eui.c`), counted at the pin:

| Group | Programs |
|---|---|
| Window systems and editors | `rio`, `acme`, `samterm` (with `sam`), `vt`, `ktrans` |
| Browsers and viewers | `mothra`, `abaco`, `page`, `jpg`, `gif`, `png`, `ppm`, `bmp`, `ico`, `tga`, `tif`, `v210`, `yuv`, `image/crop`, `image/histogram`, `vncv`, `vdiff`, `gview`, `proof`, `plot`, `fplot`, `histogram`, `trace`, `faces` |
| Tools | `stats`, `clock`, `bar`, `colors`, `fontsel`, `kbmap`, `lens`, `mug`, `paint`, `screenlock`, `spred`, `tweak`, `winwatch`, `evdump`, `flambe`, `aux/statusbar`, `aux/statusmsg`, `ip/gping`, `factotum`'s `fgui`, `audio/zuke`, `bitsy/keyboard`, `bitsy/prompter` |
| Games | `2600`, `c64`, `gb`, `gba`, `md`, `nes`, `snes`, `doom`, `blabs`, `blit`, `catclock`, `galaxy`, `glendy`, `juggle`, `life`, `mahjongg`, `mandel`, `memo`, `mines`, `mole`, `packet`, `rotzoomer`, `sokoban`, `sudoku`, `swar`, `timmy`, `turtle`, `4s`, `5s` |
| Excluded | `vmx` (needs VT-x inside the guest), `camv` (needs a USB video device), `bitsy/pencal` (needs an iPAQ touchscreen) |

That is 83 programs, 80 of them in the claim. `r9 census --gui` regenerates the list at every pin. A new program joins the claim with a test script, or the claim fails. A program leaves only when 9front deletes it.

**On which hosts.**
- macOS 15 or later on Apple Silicon, running arm64 binaries;
- Linux 6.8 or later on amd64, running amd64 binaries;
- Linux on arm64, running arm64 binaries, when an arm64 Linux builder exists (open question 6).

A host runs binaries of its own architecture. Running amd64 Plan 9 binaries on Apple Silicon is not claimed: Rosetta translates only Mach-O and Linux ELF (17, question 5).

**Unmodified.** These things are unmodified:
- **The binaries.** They are the `a.out` files the R build (or the G build) installed, byte for byte.
- **The user space.** Everything the program sees is the 9front root of the same build: `rio`, `kbdfs`, `plumber`, `factotum`, fonts, `/lib`.
- **The kernel source.** The `9h` kernel is built in the guest from `/sys/src/9/port` and the tree's arch files at the pin, with no file changed, plus `9h`'s own new drivers. That is checked by hash at each build (10.2).

**Passes.** Each program has a script in `rucc-plan9/gui/<prog>.r9`. A script starts the program in a `rio` window of fixed size, feeds it input through `/dev/mousein` and `/dev/kbdin`, waits until it is quiet, and reads back `/dev/wsys/N/window`. The image is compared against the same script run on G/Q. Each script is one of three classes:
- **exact:** the bytes are equal;
- **masked:** the bytes are equal outside declared rectangles, such as the hands of `clock`, the graphs of `stats`, or the cursor;
- **smoke:** the program draws, takes input, and exits on its quit key without a fault.

At least 60 of the 80 must be exact or masked. A script may only be smoke if the program draws nondeterministically by design and its masks would cover more than half the window. `doom` is not smoke: its timedemo is deterministic (12.6).

**Usable.** On each host, H passes the interactive checks of 11.9:
- keyboard layouts and modifier keys;
- mouse chords and scrolling;
- resizing;
- HiDPI;
- snarf to and from the host clipboard;
- audio out;
- opening a host file from `acme` through `/mnt/term`.

These are checked by `r9 hostcheck`, which drives the host window through the platform's accessibility or test interfaces (11.9).

## 02.8 What carries the claim

The graded rows are `amd64` and `arm64`, on the sets of 02.4. A run is graded only if:
- its census shows `ref-c` = 0 and no `R9_BRINGUP`;
- it ran on a builder of 04.4 with the pinned tools;
- G's baseline for the same pin exists.

Every report states its census on the first line (14.7).

## 02.9 rucc stays a GCC 16 compiler

Nothing in this folder may change rucc's behaviour on any non-Plan 9 target. Every Plan 9 feature hangs off the `plan9` OS in the target triple or off an explicit flag:
- `-fplan9-extensions`, with GCC 16's exact semantics;
- `-fkencc`, the whole dialect;
- `-mabi=kencc`.

`rucc-compat`'s GCC 16 suite must show no new failure at any milestone. `-fplan9-extensions` is tested against GCC 16 as a GCC flag, on every Linux target (06.10).

## 02.10 What does not count

- **A build that passes with a `mkfile`, header or source edited.** This includes an edit "only to add a cast".
- **A GUI that runs because the program was rebuilt for the host** (the plan9port model), and not as the 9front `a.out`.
- **A `9h` whose `port/` differs from the pin's by any byte.** It is checked by `r9 9h verify`.
- **G built by anything but kencc from the same pin,** or by a kencc older than the pin's.
- **A benchmark that is not in the declared set,** or that was added after a result was seen (13.1).
- **Screenshots compared by eye.**
